** LeetCode 1606: Find Servers That Handled Most Number of Requests

# Problem Understanding
---

We are given:

- "k" servers, numbered from "0" to "k-1".
- "arrival[i]": Arrival time of request "i".
- "load[i]": Time required to process request "i".

** Rules

1. Request "i" prefers server "i % k".
2. If the preferred server is busy, assign the request to the next available server in circular order.
3. If all servers are busy, drop the request.
4. A server becomes available when its previous request finishes.
5. Return all server IDs that handled the maximum number of requests.

---

## Understand the Problem

** Interview Explanation

"Let me first understand the problem.

We have K servers, and requests arrive at different timestamps. Every request has a processing time.

Each request has a preferred server determined by its index modulo K. If that server is busy, we need to find the next available server in circular order.

If all servers are busy, we drop the request.

Finally, we need to return the servers that handled the maximum number of requests."

** Important Observation

We need to maintain two types of information:

1. Which servers are currently available?
2. When will currently busy servers become available?

---

## Initial Intuition

"My initial thought is that for every incoming request, I need to identify the next available server starting from its preferred server.

To do this, I need to know which servers are busy and which are available.

I also need to track the finishing time of every busy server because a server should become available once its processing is completed."

This breaks the problem into two smaller operations:

- Finding the next available server.
- Releasing servers whose requests have finished.

---

# Brute Force Approach
 
** Intuition

--- 
"The most straightforward approach would be to maintain an array representing the availability and finishing time of every server.

For every incoming request:

1. Calculate the preferred server using "i % k".
2. Start checking servers from the preferred server.
3. Traverse servers in circular order.
4. Find the first server whose finishing time is less than or equal to the current arrival time.
5. Assign the request and update its finishing time.
6. If no server is available, drop the request."
---

### Example

Suppose:

"k = 3"

Available servers: "[0, 1, 2]"

Request index: "4"

Preferred server:

"4 % 3 = 1"

If server 1 is busy, check server 2.

If server 2 is also busy, wrap around and check server 0.

If server 0 is also busy, drop the request.

## Complexity Analysis
---
For every request, we might need to check all K servers.

- Time Complexity: "O(n * k)"
- Space Complexity: "O(k)"

"This approach is correct, but repeatedly scanning all servers for every request can become expensive.

I think we can optimize the server-selection process by maintaining available servers in a suitable data structure."

##  Identify the Bottleneck

Looking at the brute force approach, I identify two expensive operations:

** Bottleneck 1: 

  - Finding the next available server

We repeatedly scan servers to find the next available server in circular order.

Can we maintain available server IDs in sorted order and directly find the next available server?

** Bottleneck 2: 
  - Finding completed servers

For every incoming request, we need to identify which busy servers have completed their processing.

Can we efficiently retrieve the server with the earliest finishing time?

## Optimization Direction
---

I need two data structures:

1. An ordered set for available servers.
2. A min heap for busy servers.

---

##  Optimized Approach: Set + Min Heap

A. ** Ordered Set ** : Available Servers

set<int> available_servers;

Initially, insert all server IDs.

Example:

"available_servers = {0, 1, 2, 3, 4}"

** Why set?

- Maintains server IDs in sorted order.
- "lower_bound()" finds the smallest available server greater than or equal to the target.
- Insertion and deletion take "O(log k)".

This helps us solve the circular server-selection problem efficiently.

B.** Min Heap ** : Busy Servers

typedef pair<int, int> P;
// {finishTime, serverId}

priority_queue<P, vector<P>, greater<P>> busyServers;

The min heap stores:

"{finishTime, serverId}"

Why min heap?

We need to identify the server that finishes its request earliest.

The minimum finishing time is always available at the top of the heap.

When:

"finishTime <= currentArrivalTime"

The server has completed its request and can be moved back into the available set.

#  Complete Optimized C++ Solution
```cpp
class Solution {
public:
    typedef pair<int, int> P; 
    // {finishTime, serverId}

    vector<int> busiestServers(
        int k,
        vector<int>& arrival,
        vector<int>& load
    ) {

        set<int> available_servers;

        for(int i = 0; i < k; i++) {
            available_servers.insert(i);
        }

        priority_queue<P, vector<P>, greater<P>> busyServers;

        vector<int> countRequests(k, 0);

        for(int i = 0; i < arrival.size(); i++) {

            int time = arrival[i];

            // Step 1: Release completed servers
            while(!busyServers.empty() &&
                  busyServers.top().first <= time) {

                int server = busyServers.top().second;

                busyServers.pop();

                available_servers.insert(server);
            }

            // Step 2: Drop request if no server is available
            if(available_servers.empty()) {
                continue;
            }

            // Step 3: Find preferred server
            int target = i % k;

            auto it = available_servers.lower_bound(target);

            // Step 4: Circular wrap-around
            if(it == available_servers.end()) {
                it = available_servers.begin();
            }

            // Step 5: Assign request
            int targetServer = *it;

            available_servers.erase(it);

            busyServers.push({
                time + load[i],
                targetServer
            });

            countRequests[targetServer]++;
        }

        // Step 6: Find maximum requests handled
        int maxNumberOfRequests =
            *max_element(
                countRequests.begin(),
                countRequests.end()
            );

        vector<int> result;

        for(int i = 0; i < k; i++) {
            if(countRequests[i] == maxNumberOfRequests) {
                result.push_back(i);
            }
        }

        return result;
    }
};
```

# Interview Follow-up Questions

Q1. Why did you use a set instead of an unordered_set?

Because I need sorted server IDs and successor lookup using "lower_bound()".

An unordered set does not maintain sorted order and does not provide this operation.

Q2. Why use a min heap?

Because we need to release the server with the earliest finishing time.

A min heap gives us access to that server in "O(1)" and supports insertion/removal in "O(log k)".

Q3. Why use "<= time" instead of "< time"?

Because if a server finishes exactly when a new request arrives, it is already available to handle that request.

Q4. Why do we use "i % k"?

It determines the preferred server for request index "i".

Q5. Why do we need circular wrap-around?

If no available server has an ID greater than or equal to the preferred server, the problem requires us to start searching again from server 0.

Q6. Why do we use "while" instead of "if" when releasing servers?

Multiple servers can finish before the next request arrives, so we must release all completed servers.

Q7. Can we optimize further?

Yes. A segment tree or other specialized data structures can support successor searches, but the ordered set and min heap provide an efficient and clean solution for the given constraints.

#  My Interview Script: How I Would Explain This Problem

Interviewer: How would you approach this problem?

"My initial thought is to maintain the availability and finishing time of every server.

For every incoming request, I can calculate its preferred server using "i % k" and scan servers in circular order until I find an available one.

However, this brute force approach can take O(n × k) time because I may need to scan all servers for every request.

I notice that there are two repeated operations: finding the next available server and identifying servers that have completed their requests.

To optimize the first operation, I would use an ordered set because I need sorted server IDs and successor lookup using "lower_bound()".

For the second operation, I would use a min heap because I need to efficiently retrieve the server with the earliest finishing time.

For every incoming request, I first release all completed servers from the min heap and insert them back into the ordered set.

Then I calculate the preferred server using "i % k". I use "lower_bound()" to find the next available server. If no suitable server exists, I wrap around to the beginning of the set.

If the set is empty, I drop the request.

Otherwise, I assign the request, remove that server from the available set, insert its finishing time into the min heap, and increment its request count.

Finally, I find the maximum request count and return all servers that achieved it.

The overall time complexity is O((n + k) log k), and the auxiliary space complexity is O(k)."

# My Learning Takeaways

What I learned from this problem

1. Use an ordered set when sorted elements and successor lookup are required.
2. Use a min heap when processing depends on the earliest finishing time.
3. Use "lower_bound()" to solve circular successor selection efficiently.
4. Release completed resources before assigning new work.
5. Separate independent operations into suitable data structures.

## Core Pattern

Ordered Set + Min Heap

- Ordered Set → Which resource should I assign next?
- Min Heap → When does a resource become available again?

# My Mental Model

Whenever I encounter a resource-allocation problem:

1. Identify available and occupied resources.
2. Determine how to select the next valid resource.
3. Determine when occupied resources become free.
4. Choose data structures for both operations.
5. Maintain the state after every allocation.

Final Lesson: Don't memorize the Set + Min Heap solution. Understand why each data structure is solving a different part of the problem.
